我手上有几台机器，每台都跑着 dsh（DeepSeek Harness）。本来用法很土：
哪台要干活就 SSH 上去敲。机器一多就崩了 —— 我在外面只有手机。

后来想到个偷懒的办法：**把它们全拉进一个 QQ 群**。

现在我在群里 @ 谁，谁就接活；干完在群里回报；我在旁边看着，不满意随时插一句。

这篇写的就是这套东西怎么搭起来的。**大部分是我们本机的真实配置和踩坑记录**
（那台机器的 QQ 机器人现在就在线），少数我没实测的地方我会标出来。

## 为什么是 QQ 群

为什么不用正经的消息队列或者 Web 面板？三条：

- **群天然是消息总线**：谁发了什么、谁回了什么，所有 bot 在同一处看得见，
  不用自己写转发和订阅。
- **人能在旁边看、随时插话**：自动化最怕闷头干错事没人发现，群聊把过程摊在明面上。
- **机器人本来就在群里**，不用额外写前端，手机上就能指挥。

说白了：我不要"管理后台"，我要一个**随时能说话的地方**。

## 搭起来

### 1. 建机器人 + 装插件

去 QQ 开放平台建一个 Bot 应用，拿到 **AppID** 和 **AppSecret**，把机器人拉进群。
（入口和审核流程会变，官方文档比我说得准。）

然后给 dsh 装插件。我用的是 `@tencent-connect/dsh-qqbot`（本机 `^0.5.0`）：

```bash
# 在你的机器上执行
npx @deepseek-ai/dsh plugin --profile qqbot add @tencent-connect/dsh-qqbot
npx @deepseek-ai/dsh --profile qqbot
```

**第一次启动会进扫码引导**：终端打出二维码，手机 QQ 扫一下绑定，凭据存进 profile，
以后不用再扫。不想扫码就走环境变量：

```bash
export QQBOT_APPID="你的AppID"
export QQBOT_SECRET="你的AppSecret"
npx @deepseek-ai/dsh --profile qqbot
```

### 2. 配置

写在 profile 的 `cordis.patch.yml` 里，核心两行凭据，其余是行为开关
（下面都是本机在用的）：

```yaml
- id: im-qqbot
  name: '@tencent-connect/dsh-qqbot'
  config:
    appId: '<你的 AppID>'
    appSecret: '<你的 AppSecret>'
    cwd: '/path/to/agent/workdir'
    requireMention: true        # 群里必须 @ 它才理，默认就是 true
    streaming: false            # 关掉流式，一条一条发
    textChunkLimit: 4500        # 单条消息上限，超了自动切
    sessionIdleTimeout: 1800000 # 30 分钟没说话就换新会话
    access:
      c2cMode: open
      groupMode: open
```

两个特意调过的：

- **`requireMention: true`**：群里必须 @ 才触发，否则几个 bot 同群会互相刷屏。
- **`streaming: false`**：流式一个字一个字蹦，手机上看不像人，改成攒完发一条。

## 舰队怎么运作

「舰队」这词听着中二，但确实是这么回事：每台机器是一个**节点**，各有名字和分工。

我们这边真实的分工：

| 节点 | 干什么 |
|---|---|
| 主调度（本机） | 接令、拆单、派给别人、验收 |
| 边缘设备 | 归档巡逻、推送 |
| 云服务器 | 调研、渲染、生成 PDF |
| 一台笔记本 | 长期掉线，已从派单名单划掉 |

### 靠 @ 点名

群聊里最要紧的规矩是：**这句话是给谁的。**

我们用 **@**：给谁派活就 @ 谁，干完也 @ 回派单方。**纯叫名字不算数** ——
群里 @ 是唯一能保证对方真的收到并触发的方式。少了这个 @，活就悬在半空。

### 汇报链路不许越级

规矩是我定的：**被派单的节点回报给派单方，不直接找我**。

这样一件事的上下文都集中在主调度那儿，不会出现"三个机器人各说各的"。

**还有一条：禁止 bot 之间互相 @ 接龙。** 两个机器人互相 @ 能无限刷下去，
群里半小时就被灌满。

### 什么时候必须闭嘴

群里几个 bot 最怕**互相回话**，所以有条硬规矩：

> 没派到我头上的事，保持安静。

但有个关键例外：**被上级代理派来的子任务照常执行，不适用"保持安静"**。
子任务是明确派给它的，不是它自己"看见"的 —— 这两种情况必须分开，
否则主调度派下去的子任务会被"安静原则"吃掉。

### 人怎么在旁边看和接管

用群聊最大的好处：**我全程可见**。

派单我看着，不对就立刻说"这个先别做"；回报我看着，方向错了当场纠；
随时 @ 某个节点改主意，不用去它机器上。

## 踩过的坑

### 坑一：开机后机器人是死的，它自己不会重试

**现象**：机器重启后 QQ 一整天没反应。**根因**：开机时 DNS 还没就绪，
QQ SDK 首连失败后**自己不会重试**，就这么死了（日志里从 `apply() called` 之后再无连上记录）。
我们遇到两次，有一次是我发现"怎么一整天没人吭声"才查出来的。

**修法**：加看门狗，判断本次 dsh 启动以来 journal 里有没有出现过 `Bot ready`：

```bash
# 判定：本次启动以来有没有连上过
out=$(journalctl -u dsh.service --since "$START_TS" --no-pager 2>/dev/null)
ready_n=$(grep -c 'im-qqbot] Bot ready' <<< "$out" 2>/dev/null)
```

没有就重启 dsh 主进程，systemd 把它拉起来，机器人跟着重连。

**为什么用 systemd timer 而不是 cron**：最初挂 crontab，那条项后来**莫名其妙丢了**，
从此没人看着。timer 跟着单元走，不会自己消失。

### 坑二：看门狗把活着的机器人判成掉线（SIGPIPE 假掉线）

**现象**：机器人明明活着（十几分钟前还有 `Bot ready`），看门狗却判定"从未见过 ready"，
把 dsh 重启了，网页端跟着闪断。

**根因**：脚本开了 `set -o pipefail`，判定却写成管道：

```bash
# 元凶就是这个写法
if ! printf '%s' "$out" | grep -q 'im-qqbot] Bot ready'; then
```

`grep -q` 命中第一处就退出，可 `printf` 还在灌数据 → 吃 **SIGPIPE**（退出码 141）→
`pipefail` 把整条管道判失败 → `if !` 成立 → 把"活着"当成"没见过" → 误杀。

**只有 journal 窗口大于管道缓冲（约 64KB）才触发**，所以小窗口那轮判对、
大窗口那轮（860KB）翻车 —— 这种跟数据量有关、时好时坏的 bug 最难查。

**修法**：用 here-string + `grep -c` 替掉管道。没管道就谈不上 SIGPIPE，
而且 `grep -c` 必须读完输入才敢报数：

```bash
ready_n=$(grep -c 'im-qqbot] Bot ready' <<< "$out" 2>/dev/null)
```

我把它写成了红线：**有 `pipefail` 时，`grep -q`/`head -n`/`grep -m1`
这类"消费者可能提前退出"的管道都是雷。**

### 坑三：QQ 的"被动回复"有限额

不是猜的，插件源码里明写着（`reply-limiter`）：

- **同一条消息最多被动回复 4 次**（源码里注释写着"默认 4，留 1 次余量"）；
- **消息 ID 1 小时过期**；
- 限额用完或者过期之后，**就不能再被动回复了**，得降级成**主动消息**（不带 msg id 发）。

意思是：机器人长篇大论分 6 条发，**第 5 条开始就可能发不出去**，
表现是"回了前几条，后面没了"。对策：

- 重要的别靠 QQ 传 —— **发不出去就换通道**（本机还有微信通道兜底）；
- 正文尽量压在一条里（切多了容易撞限额）；长内容写成文件发。

### 坑四：同一个群里多个机器人抢话

我们的 bot 有 `requireMention: true` 兜着，所以它只认 @。
但**只要你手动 @ 错一个**，或者两个 bot 恰好都被 @，它们就可能互相接上话。

对策就是前面说的两条死规矩：**禁 bot 互 @ 接龙 + 没派到我头上保持安静**。

### 坑五：私聊和群聊不是一回事

**群聊**：`requireMention: true`，不 @ 不理，另外要写群规（谁该安静、怎么回报）。
**私聊**：默认"随便聊"，但你想让它干活就得单独写规则。

我们这边私聊干脆定成**只闲聊、不谈任务**，并在 prompt 里写死：回复控制在 1-3 行、
**发语音的那一轮不许再有文字**（要么纯语音要么纯文字，不出第三个气泡）。
不写清楚，它会在私聊里给你发一大段工作汇报。

### 坑六：消息太长、发文件失败

- 文本有上限，插件自动切（`textChunkLimit`），但碎块观感差，尽量自己控制长度。
- **发文件有路径白名单**：默认只允许 `media 目录 + cwd + 额外配置的目录`。
  让它发 `/etc/xxx` 会被拦住 —— 是好事，但第一次遇到会懵。
- 媒体文件有 **TTL（我们配 24 小时）**，过期自动清掉。

## 安全边界

几条硬规矩：

1. **凭据只放在机器上**：AppID/AppSecret 写进 profile 配置文件（权限收紧）或走环境变量，
   **绝对不要贴到群里**。
2. **群里说的话就是公开的**：给它明确指令，不要在群聊里复述 token、路径、内网地址。
3. **谁能指挥它要写清楚**：插件有 `access`（`c2cMode`/`groupMode` 可设
   `open`/`allowlist`/`disabled`）。固定群、固定人用就该上白名单，别开 `open`。
4. 别人把你机器人拉进群或私聊它，它一样会回应 —— 所以第 3 条不是可选项。

## 和 Tailscale 那套怎么配合

这两件事其实是两层，互不冲突：

- **Tailscale 管"机器之间怎么看到对方"**：机器在家还是在云上都无所谓，
  同一张 tailnet 里就是一个内网。写在
  [把自己几台机器连成一张网](/posts/self-host-tailscale/)。
- **QQ 管"消息怎么传"**：人在哪都能收能发，看见全过程。

合起来的好处是：**机器在哪不重要**。我在群里 @ 一下云服务器，它干完回报 ——
我不需要知道它的 IP，也不需要能直接连上它。而且坏了一层还有另一层：
QQ 限额发不出去能走微信，Tailscale 断了还能用 QQ 让它自己修。

## 最后

这套东西最大的价值不是"自动化"，而是**可见** —— 多机、多 agent 协作最容易失控的
就是"你不知道它在干嘛"，群聊天然把过程摊开了。

如果你也在管好几台机器，可以试试：**先建个群，拉一个机器人进去，让它能收发消息**。
剩下的规矩（谁 @ 谁、什么时候闭嘴、怎么回报）边跑边定，踩两次坑就知道该写什么。

> **哪些是实测**：本机的机器人配置、扫码绑定、看门狗那两次真实故障与 SIGPIPE 那个 bug、
> `reply-limiter` 的限额数字，都是真实跑出来的。群里其它节点（云服务器上跑的是另一个
> 机器人框架）的分工真实存在，但**它那边的具体配置我没上去实测过**，是按协作约定写的。
